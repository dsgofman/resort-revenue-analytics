# Architecture — dbt-resort-analytics

## Stack
- **dbt-duckdb** (`>=1.9,<2.0`) as the transformation engine, DuckDB as the default
  warehouse (`resort.duckdb`, zero-setup, gitignored — regenerated by `dbt build`).
  Same project runs unchanged on **Snowflake** via `--target snowflake` (see
  `profiles.yml`; no credentials committed, read from env vars).
- **dbt_utils** package (`packages.yml`) — used for `dbt_utils.date_spine` in
  `dim_date.sql`.
- **Streamlit** app (`ai_analyst/`) as the AI-analyst UI, **DuckDB** (read-only
  connection) for query execution, **Altair** for charts.
- **Claude Code CLI** (`claude -p`, headless, no API key) as the NL→SQL engine — see
  60_INTEGRATIONS.md.
- **GitHub Pages** hosts the static `dbt docs generate` output (`docs/`) for the public
  model-docs/lineage site.

## Warehouse layering (`models/`)
```
staging/       views, 1:1 with raw sources (models/staging/_sources.yml → data/raw/*.csv)
  stg_agents, stg_bookings, stg_commissions, stg_guests, stg_payments, stg_resorts
intermediate/  ephemeral, joins/enrichment
  int_booking_payments, int_bookings_enriched
marts/core/    tables — conformed dims + fact
  dim_agent, dim_date (dbt_utils.date_spine), dim_guest, dim_resort, fct_bookings (incremental)
marts/finance/ tables — the headline mart
  fct_commissions, fct_revenue_reconciliation (booked-vs-recognized, the $2.64M variance)
```
Materializations are set project-wide in `dbt_project.yml`
(staging=view, intermediate=ephemeral, marts=table).

Supporting: `snapshots/snap_resorts.sql` (SCD2, `check` strategy), `macros/cents_to_dollars.sql`,
`tests/assert_reconciliation_ties_to_bookings.sql` (singular test — reconciliation must
tie to fct_bookings to the cent), a dashboard `exposure` in `models/marts/finance/_finance.yml`
(documents a hypothetical downstream consumer in the lineage graph).

## AI analyst data flow (`ai_analyst/`)
```
question (Streamlit UI, app.py)
  -> schema_context.py   builds a compact schema string, but ONLY for the whitelisted
                          mart tables (ALLOWED_TABLES) — staging/intermediate are invisible
                          to the model by construction
  -> generator.py         nl_to_sql(): shells out to `claude -p` (claude_nl_to_sql) if the
                          `claude` CLI is on PATH; on any failure/absence, falls back to
                          demo_nl_to_sql() (keyword-matched canned queries) so the app
                          always works, offline-capable
  -> guardrails.py         validate_sql(): single statement, must start SELECT/WITH, no
                          DDL/DML keywords, every referenced table in ALLOWED_TABLES
                          (CTE names exempted), LIMIT enforced/appended
  -> DuckDB                connection opened `read_only=True` — defense in depth even if
                          a query somehow slipped the gate
  -> app.py                renders result table + an Altair chart
```
The gate (`guardrails.py`) and the allowed-table whitelist (`schema_context.py`) are the
two files that define "governed" here — read both before changing what the AI analyst
can see or do.

## Data
`data/raw/*.csv` (agents, bookings, commissions, guests, payments, resorts) are
Faker-generated by `scripts/generate_data.py` and **committed on purpose** (see
`.gitignore` comment) so `dbt build` works on a fresh clone with no generation step.
Regenerating them changes the demo's headline numbers ($21.90M booked / $19.25M
recognized / $2.64M variance) — don't run `generate_data.py` casually.
